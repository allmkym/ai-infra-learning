# 网页端 GPT 教学工作流

这是一份已填入当前 Modern C++ 学习起点的仓库模板。准备方式：将本目录内容放在新建学习仓库的根目录，填写仓库地址和分支，再通过网页聊天验证实际连接能力。

目标是让切换聊天后能够恢复可核验的教学状态，并减少反复解释背景。它不能保证模型永不遗忘，也不能把语气自信等同于教学正确。

## 文件分工

| 文件或目录 | 用途 | 新聊天是否读取 |
| --- | --- | --- |
| HANDOFF.md | 唯一交接入口：当前状态、证据边界、下一步及维护规则 | 必读 |
| TEACHING.md | 稳定背景、教学方式、评估标准及操作约定 | 必读 |
| ROADMAP.md | 六阶段课程与通过标准 | 必读，重点关注当前阶段 |
| exercises/ | 题目、源码、输入和构建说明 | 当前任务需要时 |
| records/ | 验收依据、关键原始回答与历史结论 | 按需，禁止全量加载 |
| PROMPTS.md | 新聊天、保存、代码审查等现成指令 | 由用户复制使用 |

HANDOFF.md 采用覆盖式更新，目标不超过 2500 个字符、120 行。历史可以增长，但每次聊天的必读材料应保持短小。稳定文档只有必要变化时才修改；达到阶段里程碑可归档当前阶段的详细记录，不删掉未来需要的证据。

## 第一次使用

1. 创建一个专门学习仓库并上传本目录。可先使用一个 main 分支，避免为每次小练习增加分支负担。
2. 在 HANDOFF.md 填写真实仓库和状态分支，把“本地初始化”改为实际情况。首次上传之后才能说已保存到 GitHub。
3. 在网页端连接所需 GitHub 插件或工具，使用 PROMPTS.md 第 5 条检查读取、指定版本读取、写入和回读。这个模板没有替你检查账号权限。
4. 如果使用 ChatGPT 项目，把 PROMPTS.md 第 1 条放入项目说明。不要把经常变化的 HANDOFF.md 再上传为另一份长期副本；避免项目附件与仓库同时维护两个当前状态。
5. 新开聊天，使用第 2 条指令。检查它是否正确说出“诊断结束、第 1 阶段尚未通过、提示后修复程序、当前暂停新课”，以及 next step 的含义。
6. 恢复正确后，用户明确提出继续教学。首次演练失败时先修复读取／版本／状态记录问题，不通过复制全部旧聊天来掩盖问题。

项目功能是便利选项，普通新聊天也能按相同指令恢复。如果希望尽量隔离过去的闲聊，普通新聊天加明确文件读取同样可用；不要假定在项目内新建聊天就必然完全隔离其他聊天的影响。

## 日常循环

教师读取状态并教学 → 学员编码、查文档和本地验证 → 学员 commit / push → 教师读取指定提交审查 → 学员修复与解释 → 教师按证据更新状态 → 保存并回读 → 继续或换聊天。

保存与换聊天是两个独立动作。建议在有意义的练习验收、一天结束、路线改变后保存；阶段结束自然换聊天，质量明显下降时提前换。没有新事实的每条对话不必写仓库。

每次读取要尽可能固定到具体提交。提交 SHA 是版本依据；聊天标题、“最新代码”或一次搜索命中不能替代它。工具无法给出或读取 SHA 时如实注明；最低可核对状态版本、文件内容与末尾标记，但这种核对不等于验证了精确代码版本。

## 写入能力与失败处理

- 能直接提交：保存关联文档后回读，报告 commit 链接、目标分支和状态版本。
- 只能创建 PR：PR 提交成功不等于 main 已更新。合并后确认目标分支，或明确让下个聊天读取该 PR 分支／提交。
- 只能读取：教师生成完整替换版交接文件，用户本地替换后 commit / push。这只需搬运短文件，不需要搬运聊天记录。
- 只能搜索摘要：不能据此声称读完交接文档。尝试明确文件路径或受支持的完整读取；仍不可用时只上传当前三份核心文档。
- 当前聊天已遗忘：从最后已确认保存的检查点恢复；缺失的几步依据代码、原始回答或用户简短补充重建，不能靠猜测补齐。
- 同时出现两个教学聊天：只让一个保存状态。另一个输出结论和证据交回主聊天；真正冲突时保留双方事实并向用户说明具体分歧。

教师写远程文档后，用户下一次修改前要先同步远程。若本地工作区干净，可使用 git pull --ff-only；有未提交修改或分支分叉时先查看状态并处理，不使用强推或强制重置当作常规同步办法。

## 教学质量如何检查

每个单元都有明确目标与验收要求，先讲解再练习，按需递进提示；查 API 允许。教师完整示范后学员照写可以算练习，不直接升级为独立掌握。

重要知识在后续不同场景中再次使用；是否通过依据限定任务和解释，不能因为编译通过或教师说“掌握了”就完成整章。未评估内容保持未评估。

发现教师前后矛盾时，要求指出对应代码版本与依据；对 C++ 语义结合可靠资料和最小实验核对。一次运行无报错不能证明生命周期、并发或未定义行为问题不存在。

## 产品能力依据与限制

核对日期：2026-09-22。官方说明插件可向受支持的 ChatGPT 界面提供工具，具体动作依赖所安装插件、连接和权限；这不能证明某一用户的网页聊天已经可写 GitHub。[官方插件文档](https://learn.chatgpt.com/docs/plugins)

ChatGPT 项目可组织聊天、文件、说明及连接来源；本方案只把它当固定启动约定的容器，教学当前状态仍以指定仓库版本为准。[官方项目文档](https://learn.chatgpt.com/docs/projects?surface=web)

本方案不依赖关于网页端隐藏的上下文压缩机制、精确窗口大小或额度无限的假设，也不要求开通 API、自建数据库或自动定时写入。
